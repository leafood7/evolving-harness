# 工作方法对照：验收脚本与试跑准备

这里固定了来自本地 log-inspector 的11个文本源文件，基线有31项测试。它是用户项目的评测快照，示例日志均为合成数据，不包含用户数据库或历史会话。任务是根据项目现状提出的功能、修复和重构需求，不冒充已有生产事故或真实客户工单。

## 校准10项检查

从 Harness 源码根目录运行，输出路径必须不存在：

```powershell
python benchmarks/log_inspector/calibrate.py --output .harness/grader-calibration-001.json
```

每题检查三种临时副本：尚未实现新需求的原代码应失败；人工编写的正确实现应通过；违反关键规则的错误实现应失败。正确实现还必须通过原31项隔离回归。所有改动只发生在带校准标记的临时目录，拒绝直接修改冻结源文件。报告同时记录检查脚本哈希和源文件不变性。

这些是验收器的正反例，不是 Agent 解决任务的成绩，也不是进化有效的证据。`fixtures.py` 中的正确答案、错误答案和完整评分代码不会放入模型的源码副本。当前用户权限下的 Shell 仍能访问副本外路径，不能把目录隔离说成 OS 沙盒。

## 准备两题小试

`prepare_pilot.py` 读取已准备的 protocol.json、development-tasks.json、baseline-skill.json、candidate-skill-draft.json 和 frozen-source/。它只选择 dev-01（聚合诊断计数）与 dev-05（提取聚合模块），不读取预留任务文件。示例：

```powershell
python benchmarks/log_inspector/prepare_pilot.py --preparation 路径/工作方法对照准备 --calibration 路径/校准报告.json --output 路径/新的小试目录
```

准备时核对起点、Skill及验收代码哈希；创建新的独立数据库，复制旧Skill并登记未启用候选。两组共用空项目记忆和空用户偏好、相同基础指令、源码及检查。检查脚本冻结为内联Python文本，而不是运行一个可能被改写的外部评分文件。已有文件的允许修改范围转换为受保护文件；新增文件范围仍主要依靠任务约束和人工复核。

`prepared.json` 标为 PREPARED_NO_MODEL_RUNS；报告也应显示待运行。打开原生Pi时须指定该文件中的数据库、用户、项目和工作区，然后执行 `/harness eval run`，查看完整载荷并确认后才启动四次任务执行。候选在实验数据库中供比较，未成为正式项目的活动版本；准备不调用模型。

准备和评分者信息不应成为模型任务提示。尤其是“独立验收会运行隔离测试”不应被拼入普通功能任务，让 Agent 误以为用户要求它也无条件运行相同检查。

## 能检验什么

自动检查覆盖功能与接口契约；独立回归覆盖原行为。是否主动做了必要检查、是否多做无关检查，要结合原生工具轨迹另外判断；功能检查通过不等于工作流决策正确。

这批任务来自同一个项目，不证明跨项目泛化。小试仅检查试验流程能否正常工作，不应作为正式收益结论。完整重复研究所需的重复编号、开发/预留强制隔离、批次金额或用量上限、人工干预记录仍需后续实现；当前不会自动启动60次正式运行。运行时费用估算不等于提供商账单。

用户须在真实运行前查看载荷，约定时间和金额预算并确认；所有失败、平局和无结论都应保留，不能用重试覆盖结果。
